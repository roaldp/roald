## Symptom one: merge conflicts

The observable symptom is that a branch that was fine when the agent stopped working on it will not
merge when it is picked up again.

The mechanism has three steps. First, a branch is cut from `main` and then never pulls `main` back
in, so the gap only ever widens: `roaldp/ux-improvements` is eight commits behind and changes a
single file. Second, the branches are not independent, because parallel jobs land on the same few
files. Across the six live branches, `pulse.py` is modified by five of them and
`config.template.yaml` by three. `pulse.py` is a single 34 KB module that is the whole application,
so any two concurrent jobs are editing the same file by construction. Third, generated artefacts are
committed, so they collide too: `roaldp/token-monitoring-v2` conflicts on
`.docs/plans/2026.03.13-token-monitoring.md`, a planning document, not code.

The fix is one habit and one structural change. The habit is that a branch rebases onto `origin/main`
at the start of every working session and after every merge into `main`, not at the end. A branch
that is zero commits behind cannot conflict. The structural change is that `pulse.py` has to stop
being one file before parallel work on it is safe, which is a separate piece of work and is not
solved by any git rule.

## Symptom two: pull requests opened too late

The observable symptom is that the pull request is a formality, and no one ever reviews anything.

The mechanism is visible in the timestamps. Of the eleven pull requests that reached a conclusion,
the time from opening to merging was: 1 min, 3 min, 4 min, 7 min, 23 min, 65 min, and a long tail
of under a day. PR #12 was +10395/-0 and merged 23 minutes after it was opened. The pull request is
therefore not a review surface. It is created after the work is already finished, and pressed
straight away. Two consequences follow. There is no window during which the branch is visible while
it could still be steered, and there is no window during which the branch could have been kept in
sync with `main`, because the branch and the pull request only coexist for a few minutes.

The fix is to open the pull request as a draft on the first push of a branch, when it contains one
commit and no completed work. This costs nothing, and it makes every in-flight job visible in one
list. Draft means "in progress", ready-for-review means "look at this", merge stays where it is.

## Symptom three: not knowing when a job is done

The observable symptom is that nothing tells you which branches are finished, so nothing gets
deleted and old branches get picked back up by mistake.

The mechanism is that "merged" leaves no local trace. 19 local branches are fully contained in
`main` and are indistinguishable, in `git branch` output, from live work. Worse, a merged branch can
be reused: `roaldp/arch-design-agent` was merged as PR #9 on 2026-03-13, then had four more commits
added to it and was re-opened as PR #11 the next day. PR #11 is the conflicting one. Reusing a
branch after its merge is how a branch ends up with a fork point that no longer matches its pull
request.

The fix is a rule with a testable condition rather than a judgement call. A branch whose diff
against `origin/main` is empty is done: delete it locally and on the remote. A branch is never
reused after its pull request merges, a new job gets a new branch. A pull request whose branch has
not moved in fourteen days is closed, and its branch is deleted, because if the work mattered it
would have moved.

## Symptom four: jobs that run for weeks

Weeks is fine. Weeks of divergence is not. The two are separable, and the rebase habit above is what
separates them. A branch that is rebased at the start of every session can be six months old and
still merge in one commit, because the only thing that decays is the gap, not the age.

The workspace layout makes long jobs harder to track than they need to be. Three of the eleven
entries under `~/conductor/workspaces/roald/` are symlinks pointing at differently-named workspaces:
`bernard-follow-ups` points at `copenhagen`, `humanoid-capital-followup-note` points at
`st-georges`, `inspect-conductor-workspaces` points at `lima`. So the workspace name, the directory
name and the branch name are three different strings for the same job, and none of them can be used
to look up the other two.

## The proposed rule

Five lines. They are meant to be short enough to actually be followed.

1. **Rebase on entry.** Before touching a branch, `git fetch origin && git rebase origin/main`. If
   it conflicts, resolve it then, while the change set is small, not at merge time.
2. **Draft pull request on the first push.** One commit is enough. Never let a branch exist without
   a pull request pointing at it.
3. **One branch, one pull request, then delete.** Never add commits to a branch after its pull
   request has merged. A new job gets a new branch.
4. **Check the hotspots before starting.** If another open branch already changes `pulse.py`, either
   wait for it or plan to rebase onto it, rather than discovering the collision at merge time.
5. **Empty diff means delete, fourteen days stale means close.** Both conditions are mechanical and
   can be checked by a script.

## Where this would be enforced

Three places, in decreasing order of how much they change:

- `framework/skills/push_all_changes_to_git/SKILL.md` currently stages, commits and pushes. It would
  gain a rebase-onto-`origin/main` step before staging, and a step that opens a draft pull request
  if the branch does not already have one.
- `framework/rules/how-work-runs-here.md` would gain a short "Git" section carrying rules 1, 3 and 4,
  so that every agent on the machine reads them, not only the ones that invoke the git skills.
- A new sweep, which lists branches with an empty diff against `origin/main` and pull requests whose
  branch has not moved in fourteen days, and deletes or closes them. This is the only new artefact.

Nothing here is enforced by CI, because the repository has none.
